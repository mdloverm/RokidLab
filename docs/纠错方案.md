### 1.2 数据流依赖关系

```
手机端                                       眼镜端
┌──────────────────────────┐          ┌────────────────────────┐
│ AdbFileManagerClient     │──ADB──→  │ ADB daemon (系统进程)   │
│ AdbShellClient           │──ADB──→  │ ADB daemon (系统进程)   │
│ AdbScreenMirrorClient    │──ADB──→  │ ADB daemon (系统进程)   │
│ PhoneMirrorService       │──TCP──→  │ PhoneMirrorServer       │
│                          │   :7654  │                         │
│ CxrLHiRokidSession       │──BLE──→  │ CXR-L SDK (系统服务)    │
│ BluetoothHidManager      │──BLE──→  │ HID / SPP 协议          │
└──────────────────────────┘          └────────────────────────┘
```

**关键依赖说明：**
- **设备关系**：手机端为**标准 Android**，眼镜端为 **Android Go 12**（轻量系统，部分 API 可能受限）
- 三个 ADB Client 各自维护独立 Socket 连接，但**共享同一对 RSA 密钥**（通过 `AdbKeyManager`）
- ADB 认证流程：`CNXN → AUTH_TOKEN → AUTH_SIGNATURE → AUTH_RSA_PUBLIC → CNXN`
- ADB 消息头 24 字节：`command(4) + arg0(4) + arg1(4) + payloadLength(4) + checksum(4) + magic(4)`
- 投屏帧协议 5 字节 header：`方向(1) + 宽(2, LE) + 高(2, LE)` + N 字节灰度数据
- CXR-L SDK 通过反射获取内部 `ServiceConnection` 字段实现绑定

## 二、错误类型分类与检查点

### 2.1 ADB 协议层（核心风险区）

**检查要点：每次修改 ADB 相关代码时逐项核查**

| # | 检查项 | 是否通过 |
|---|--------|---------|
| ADB-C1 | 所有 `readPacket()` / `readMessage()` 消费后 `CMD_CLSE` 必须验证 `arg1 == localId` | ✅ |
| ADB-C2 | 所有 `readPacket()` / `readMessage()` 消费后 `CMD_WRTE` 必须验证 `arg1 == localId` | ✅ |
| ADB-C3 | `CMD_OKAY` 回复时 `arg1` 必须填 `msg.arg0`（即服务端的 remoteId） | ✅ |
| ADB-C4 | `CMD_CLSE` 发送时 `arg0=localId, arg1=remoteId` | ✅ |
| ADB-C5 | 所有 `while(true)` 循环必须有超时保护（`socket.soTimeout`）或明确退出条件 | ✅ |
| ADB-C6 | `localId` 递增必须线程安全（使用 `AtomicInteger`） | ✅ |
| ADB-C7 | RSA 密钥必须通过 `AdbKeyManager.getOrCreateKeyPair()` 获取，禁止每次 `generateKeyPair()` | ✅ |
| ADB-C8 | Shell 命令拼接必须转义（使用单引号包裹 + `s.replace("'", "'\\''")`） | ✅ |
| ADB-C9 | `disconnect()` / `close()` 必须释放 Socket、InputStream、OutputStream | ✅ |
| ADB-C10 | 多 Client 共享 Socket 时（若未来统一），必须添加 lock 防止并发写 | ✅ |

### 2.2 投屏协议层

| # | 检查项 | 是否通过 |
|---|--------|---------|
| MIR-C1 | 眼镜端 `receiveFrames` 读取 header 后必须校验 `frameWidth/frameHeight` 合法性 | ✅ |
| MIR-C2 | `frameWidth * frameHeight` 必须在 `ByteArray()` 前校验 `<= 0` 和上限 | ✅ |
| MIR-C3 | header 校验失败时必须跳过对应长度的数据对齐协议流（用 cap 保护 `skipSize`） | ✅ |
| MIR-C4 | `processImage` 中 `buffer.remaining()` 必须与 `minRequired` 比较 | ✅ |
| MIR-C5 | `sendFrame` 中 header 和 data 必须合并为一次 `write()`，禁止分两次 | ✅ |
| MIR-C6 | `stopMirror()` 中必须先清除 `imageHandler` 回调再关闭 `imageReader`（顺序不可逆） | ✅ |
| MIR-C7 | `createGrayscaleBitmap` 中必须先创建新 Bitmap 成功后再 `recycle()` 旧的 | ✅ |
| MIR-C8 | `VirtualDisplay` 重建期间须确保 `imageReader` 旧监听器已移除 | ✅ |
| MIR-C9 | Socket 异常时必须关闭旧 `outputStream` 再新建 | ✅ |

## 三、Master Checklist（每次修改必须逐项检查）

### 3.1 准备阶段

```
□ 读取本文档的「项目档案」了解当前最新结构
□ 确定本次修改属于：新增功能 / 修复 bug / 重构 / 删除功能
□ 确定影响范围：ADB / 投屏 / CXR-L / HID / 商店 / 构建
```

### 3.2 修改前分析

```
□ 1. 搜索项目中所有「同类模式」—— 确保修复一处、同步修复所有
   -   搜索关键词建议：readPacket, readMessage, CLSE, while(true), generateKeyPair
   -   如果修改某个流处理逻辑，检查所有三个 ADB Client 中是否都有相同模式
□ 2. 检查本次修改是否会影响其他模块的调用方
   -   API 签名变更 → 更新所有调用方
   -   构造函数参数变更 → 更新所有 new 实例的代码
   -   异常类型变更 → 更新所有 catch 块
□ 3. 检查本次修改是否引入新的资源（线程 / Socket / Bitmap）并确保释放路径
□ 4. 对照第二节所有相关检查点逐项核查
```

### 3.3 修改后验证

```
□ 1. gradlew assembleDebug 0 错误通过
□ 2. 新增代码已添加关键路径日志（用于后续排查）
□ 3. 本文档的「项目档案」已同步更新（新增文件 / 修改架构 / 变更 TAG）
□ 4. 本文档的「变更日志」已追加新的修改记录
```

### 3.4 紧急修复（P0）附加要求

```
□ 创建修复分支 hotfix/<描述>
□ 至少 1 人 Code Review
□ 24h 内完成修复 + 自测 + 合并
□ 补写复盘报告（5 Why 分析法）
```

### 4.2 数据流与协议定义

**ADB Wire Protocol**
- 消息头固定 24 字节，Little-Endian
- 命令常量：`CMD_CNXN=0x4e584e43`, `CMD_AUTH=0x48545541`, `CMD_OPEN=0x4e45504f`, `CMD_OKAY=0x59414b4f`, `CMD_CLSE=0x45534c43`, `CMD_WRTE=0x45545257`
- 认证类型：`AUTH_TOKEN=1`, `AUTH_SIGNATURE=2`, `AUTH_RSA_PUBLIC=3`
- 三次 ADB Client 均有 `sendPacket`/`readPacket` 或等效的消息读写方法

**投屏帧协议**
- 5 字节 header: `[方向(1)][宽(2,LE)][高(2,LE)]` + N 字节灰度数据
- 灰度计算公式：`gray = 0.299*R + 0.587*G + 0.114*B`
- 方向定义：`0=竖屏`, `1=横屏`

**ADB 密钥管理**
- 存储路径：`context.filesDir/adbkey`（私钥）和 `adbkey.pub`（公钥）
- 所有 ADB Client 通过 `AdbKeyManager.getOrCreateKeyPair()` 共享同一对密钥

### 6.1 优先级矩阵

```
            影响范围大    影响范围小
用户感知强      P0           P1
用户感知弱      P1           P2
```

| 等级 | 响应时间 | 修复时限 | 典型场景 |
|------|---------|---------|---------|
| P0 | 立即 | 24h | 主功能崩溃/数据丢失/安全漏洞 |
| P1 | 当天 | 3天 | 功能部分失效/性能严重下降 |
| P2 | 3天内 | 1周 | 功能可用但体验不佳 |
| P3 | 1周内 | 2周 | 视觉/体验小问题 |
